| SBOM Signer | tools/compliance/sbom_signer.py | SBOM Author Signature — the 2026 Minimum Elements element. Wraps tools/crypto/attestation_signer + key_manager; signs the canonicalized SBOM and writes a detached `<sbom>.sig.json` beside it. Approved algorithms only (FIPS 186-5 ECDSA P-256/384/521 and Ed25519) — HMAC-SHA256 and an empty signature are refused, because a symmetric MAC is not attributable to an author. Fully offline on both paths: no sigstore/Fulcio/Rekor/OCSP. Verification needs only the SBOM + signature; `--expect-fp` turns integrity into authorship. Called by sbom_generator, which persists the value + algorithm to sbom_records. Mirrored at icdev/tools/compliance/sbom_signer.py. | --sign, --verify, --key-path, --expect-fp, --list-algorithms, --json | Signature block / verification result |
| SBOM Component Producer | tools/compliance/component_producer.py | Component Producer, the 2026 SBOM Minimum Element that REPLACED Supplier Name (sbx-fld-02). Resolves the one organization that creates, defines and identifies each component, offline, from the package's own metadata — PyPI `Author`/`Maintainer`, npm `author`, a Maven POM `<organization>`, a crate's `authors`, a nuspec `<authors>` — falling back to `args/sbom_producer_registry.yaml` to turn a Go module host path or a reverse-DNS Maven groupId into an organization name. NEVER populates the producer from CycloneDX `group`, which is a namespace: `_reject_namespace_echo` drops any candidate that echoes it. A component with no identifiable producer is explicitly marked of unknown provenance with a machine-readable reason, because the standard says silence is not acceptable. Writes `manufacturer` on CycloneDX 1.6+ and `supplier` below it, plus authoritative `icdev:component-producer*` properties on every version. Library first: import `ProducerContext`, `resolve_producer`, `apply_producer_to_cyclonedx`, `producer_properties`, `producer_db_value`, `validate_sbom_producers`. Mirrored at icdev/tools/compliance/component_producer.py. | --purl \| --name/--version [--ecosystem] [--project-dir] [--python-env] \| --validate \<sbom.cdx.json\> \| --registry [--json] | {producer, provenance, source, evidence, reason}; for --validate {valid, component_count, producers_known, producers_unknown, errors[]} and exit 1 on a conformance failure |
| SBOM Revision & Frequency | tools/compliance/sbom_revision.py | SBOM 2026 **Frequency** and **Accommodation of Updates** — the two practices, one mechanism (sbx-prc-02). Every generation appends a row linked to its predecessor via `supersedes_sbom_id`; a CORRECTION is a **successor** row, never an edit, so the corrected record keeps describing the document a recipient may already hold. There is deliberately no `superseded` column — `revision_chain` derives the mark at read time from the forward links. `content_digest` digests the document with serialNumber/timestamp/version stripped, which is what distinguishes a substantive revision from a re-issue of identical content; the file hash cannot, because it never matches across two emissions. `evaluate_frequency` answers the per-build question from `source_revision` FIRST and treats `sbom_max_age_days` as the stale-evidence backstop — this is the reconciliation of CLAUDE.md's "regenerated on every build" with the 30-day gate; SBD-21 calls it. Writes `sbom_revised` / `sbom_corrected` audit events. Library first: import `content_digest`, `plan_revision`, `revision_insert_fields`, `revision_chain`, `latest_record`, `apply_correction`, `evaluate_frequency`, `next_sbom_version`, `gate_threshold`. Mirrored at icdev/tools/compliance/sbom_revision.py. | --project-id [--chain] [--frequency] [--correct --sbom \<path\> --reason \<why\> [--reason-code]] [--project-dir] [--build-id] [--json] | Revision chain with superseded/is_head marks; frequency {status, conditions[], age_days, recorded_revision}; correction {sbom_record_id, superseded_sbom_id, sbom_version, file_path} |
| SBOM Conformance Gate | tools/compliance/sbom_conformance_gate.py | Gates an SBOM on what it SAYS, not on its existence (sbx-gov-01). The five pre-existing SBOM conditions in `args/security_gates.yaml` — `sbom_not_generated`, `sbom_attestation_missing`, `sbom_stale_over_30_days`, `sbom_generation_failed`, `sbom_generation_skipped` — are presence, freshness and exit-code checks, so `{"bomFormat":"CycloneDX","specVersion":"1.4"}` clears every one. Adds `sbom_minimum_elements_not_met` (blocking) and `sbom_conformance_below_threshold` (warning), wired into `deployment_gates`, `swft` and `devsecops`. Every threshold is read from `args/security_gates.yaml` -> `sbom_conformance.thresholds`; the module holds NO default and raises `SbomGateConfigError` rather than substituting one. Scoring is delegated to sbx-sig-02's `sbom_minimum_elements_validator` the moment it is importable — the built-in structural check is an interim stand-in, and `scored_by` on every result says which ran. Component Producer is delegated to `component_producer.validate_sbom_producers`. Library first: import `evaluate_sbom_gate`, `evaluate_sbom_file`, `score_sbom`, `load_gate_config`. Mirrored at icdev/tools/compliance/sbom_conformance_gate.py. | --sbom \<sbom.cdx.json\> [--gate deployment_gates\|swft\|devsecops] [--json] | {passed, score_pct, elements_met/total, blocking[], warnings[], gaps[], scored_by, thresholds}; exit 1 when blocking, 2 when misconfigured |
