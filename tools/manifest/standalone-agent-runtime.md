# Standalone Agent Runtime (SAG)

> A persistent, interactive agent process. A thin orchestration shell over
> ICDEV's production agent loop, chat persistence, and provider abstraction —
> it introduces no new LLM execution path or storage. Canonical package:
> `icdev/tools/agent_runtime/` (mirrored to `tools/agent_runtime/`).

| `tools/agent_runtime/config.py` | Declarative runtime configuration (hgx-cfg-01) — `AgentRuntimeConfig` + `load_config()` over `args/agent_runtime.yaml`. Added **beneath** the existing environment variables, never above them: resolution is `explicit argument > env var > YAML > built-in default`, so every flag that worked before still works and still wins. Each accessor (`flag`/`integer`/`number`/`text`/`subsystem_enabled`) takes the env name it defers to and reads it first; an unparseable env value falls through a layer rather than zeroing the setting, and an out-of-vocabulary approval mode resolves to the strictest value at every layer (never `off`). | `tools/agent_runtime/inbox_channel.py` | Channel delivery + reply resolution for the approval inbox (agov-inbox-03). The mirror agov-inbox-01/02 lacked: it delivers a pending `approval_items` row to Slack/Teams/Telegram/Mattermost/email over the `BaseChannelAdapter.send_message(channel_user_id, text, thread_id)` seam every adapter already exposes, and adds **no HTTP client of its own** (asserted against the module source in `tests/test_inbox_channel.py`). **The correlation token is the design**: a delivered message carries `[icdev:<item_id>]` and `resolve_from_reply()` settles the item that token names and nothing else. A reply with NO token — or with two distinct tokens — resolves NOTHING; it is never applied to the most recent or the only pending item, because guessing which approval a bare "yes" meant is how the wrong irreversible action gets approved. | `tools/agent_runtime/inbox_adapters.py` | ACE and workflow_hitl in the unified approval inbox (agov-inbox-05). Each gate keeps its own store as the truth for its own waiter — `ace_audit_log` rows (`hitl_pending`, released by INSERTing a matching `hitl_resolved`, which is what `CoWorkerThread._wait_for_hitl_resolution` polls) and `wf_approvals` rows (`status='pending'`, released by `feedback.submit_feedback`) — and `approval_items` is a MIRROR of those, never a replacement. Two consequences are the whole design. (1) **Mirroring is best-effort**: an unmigrated or unreachable inbox leaves the originating gate holding exactly as it does today, because failing the ACE gate closed on a mirror error would make an optional delivery channel load-bearing and failing it open would turn a missing table into an approval. (2) **A resolution from either side settles the other**: answering in the ACE UI (`POST /api/ace/<id>/hitl`) closes the item, and answering in the inbox INSERTs the ACE audit row and wakes the parked thread through the same `HITLGate` the UI calls. `ace_audit_log` stays APPEND-ONLY throughout — a resolution INSERTs, nothing here UPDATEs an ACE row, and the mutable state lives only in `approval_items`. `resolve()` **settles the item BEFORE releasing the origin**: `_settle` is a conditional UPDATE accepting the transition only if exactly one row changed, so settling first is what makes exactly one caller go on to release — the reverse order has no such guard and would let a Slack reply and the ACE UI both release. ## Design rule — loop or graph? (hgx-doc-02)

**[docs/patterns/loop-vs-graph-decision-tree.md](../../docs/patterns/loop-vs-graph-decision-tree.md)**
is the standing rule for choosing between this runtime and Studio's DAG runtime
(`tools/studio/workflow_runner.py`, shard:
[icdev-studio-low-code-no-code-platform.md](icdev-studio-low-code-no-code-platform.md)).

Short form: **if the steps are known ahead of time, author a graph; if the task
is open-ended, start with a plain agent loop and only add structure once a stage
has proven it always happens.** Do not force a graph onto exploratory work — a
graph node cannot look somewhere its author did not name, so the DAG quietly
turns "find out what is wrong" into "confirm the author's hypothesis". And a
graph costs materially more: `max_parallel: 4` is four concurrent contexts, each
carrying its own system prompt, project-context block and tool schemas, not one
agent doing four things.

The hybrid is the common case, and it is what `node_type: agent` (hgx-agent-01)
exists for: author the known skeleton as a graph, and make the one stage that is
not enumerable a bounded agent loop inside a node.
