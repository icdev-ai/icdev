## 3. Why was /network/ 500'ing at b1a6f6215?

Two later commits landed on `irad/feature` that repaired the network canvas on
the PG-primary backend:

| Commit  | Purpose |
|---------|---------|
| `2e9c8513c` | `fix(network): project pages work on shared PG (missing/colliding tables)` |
| `a238c1c2a` | `feat(network): PG-primary migration-phases + 6-dimension migration analysis` |

`b1a6f6215` was on the upstream timeline **between** these fixes and the
PG-primary migration of the network canvas. The CI runner was running the
E2E against a snapshot where the network canvas's `topologies` /
`simulation_results` table set and Python-side node/edge counting had not yet
been hardened, so the dashboard returned 500 on the index route's
`simulation_results` query.

The fix to the index route that later shipped in `2e9c8513c` is:

```python
# tools/network/blueprint.py:224-242
try:
    sims = [...]  # SELECT FROM simulation_results
    total_sims = conn.execute("SELECT COUNT(*) FROM simulation_results").fetchone()[0]
except Exception:
    # simulation_results may be absent/divergent on a given backend —
    # the sims widget is non-critical; degrade gracefully.
    try:
        conn.rollback()
    except Exception:
        pass
    sims = []
    total_sims = 0
```

That `try/except` degradation was not yet present at `b1a6f6215`, so any
backend divergence (CI uses `ICDEV_STORAGE_BACKEND=postgresql` per
`icdev-ci.yml`) caused an unhandled exception → 500.
