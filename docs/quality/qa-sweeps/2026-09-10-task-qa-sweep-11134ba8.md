## 6. Fixed in this PR — a run row said it STARTED when it FINISHED

`record_run` named neither `started_at` nor `completed_at`. The column default
filled `started_at` with the moment of the INSERT, which runs after the sweep,
and `completed_at` stayed NULL. Measured on this run: batches began 20:29:24Z
and the row reads `started_at 2026-09-10 20:48:47Z`; all 21 rows in the table
had a NULL `completed_at`. So every recorded sweep claimed to start at its own
finish, and no duration was recoverable from the table — the 2026-08-29 report
noted the NULL half of this and left it.

`QARunResult` now carries `started_at` / `completed_at`, stamped by
`run_e2e_suite` before the first batch and after the last (including the
no-spec early return), in the text form PostgreSQL's `CURRENT_TIMESTAMP` writes
into these TEXT columns, so the `started_at` index keeps sorting old and new
rows together. `record_run` names both columns in both dialects; an unmeasured
start still falls back to the default (the column is NOT NULL) and an
unmeasured finish is NULL, never a guess.

This run's own row was written by the pre-fix code and still shows the defect.
`ace_qa_runs` is append-only, so it is not corrected; the true times are the
ones in §2.

**Found on the way, fixed in its own commit.** Touching `record_run` put the
file in the coherence fast tier's scope, and `canvas_placeholder_style` /
`runtime_placeholder_style` flagged three SQLite-dialect `?` retries —
`record_run`, `record_failure`, `get_run_status`. They were dead on SQLite
(storage's connection already translates `%s`) and could only raise on
PostgreSQL, so their one effect was to log the retry's error in place of the
real one, and to log a spurious failure for an ordinary missing run id. All
three now speak one dialect. CI runs neither check, which is how the sites
stood.

Red-first proof for both, `python tools/ci/red_first_gate.py --files
tests/test_qa_agent_runner.py`: **discriminating** — merge base 6 failed /
81 passed, this tree 87 passed. One of the new tests is a real SQLite round
trip of `record_run` rather than a mock, and `--status` was re-run against the
live PostgreSQL board for a real run id (full row) and a missing one
(`Not found`, no error logged).
