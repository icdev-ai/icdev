# Keycloak + Windows Active Directory Integration for ICDEV™

## Executive Summary

**Yes.** Keycloak integrates natively with Windows Active Directory via **LDAP federation** (most common) and optionally **Kerberos/SPNEGO** (seamless Windows desktop SSO). AD becomes the authoritative identity source; Keycloak becomes the identity broker that translates AD users into OIDC tokens for ICDEV.

---

## Integration Architecture

```
Student / Employee
      │
      ├───(1) Logs into Windows workstation ──→ Windows AD (Kerberos ticket)
      │
      ├───(2) Opens browser → ICDEV Dashboard ──→ Keycloak detects Kerberos ticket
      │                                          → Seamless login (no password prompt)
      │
      └───(3) Keycloak issues OIDC token ──→ ICDEV validates JWT
                                           → g.current_user populated
                                           → LLM Router resolves virtual key
```

## Method 1: LDAP Federation (Recommended)

Keycloak connects to AD Domain Controllers as an LDAP client, syncing users and groups into its own database.

### What You Configure in Keycloak Admin Console

**User Federation → Add LDAP Provider:**

| Field | Example Value |
|-------|---------------|
| **Console Display Name** | `ICDEV-AD` |
| **Vendor** | `Active Directory` |
| **Connection URL** | `ldaps://dc01.corp.local:636` |
| **Bind DN** | `CN=svc_keycloak,OU=ServiceAccounts,DC=corp,DC=local` |
| **Bind Credential** | `***` (service account password) |
| **Users DN** | `OU=Users,DC=corp,DC=local` |
| **Username LDAP Attribute** | `sAMAccountName` or `userPrincipalName` |
| **UUID LDAP Attribute** | `objectGUID` |
| **User Object Classes** | `person, organizationalPerson, user` |
| **Connection Pooling** | `On` |
| **Pagination** | `On` (for large directories) |

### Group Mapping

**User Federation → Mappers → Add Mapper:**

| Mapper Type | Purpose |
|-------------|---------|
| `group-ldap-mapper` | Pull AD security groups into Keycloak realm roles |
| `user-attribute-ldap-mapper` | Map AD attributes (email, displayName, department) to Keycloak user attributes |

**Example group mapping:**
```
AD Group: CN=ICDEV-Students,OU=Groups,DC=corp,DC=local
     ↓
Keycloak Role: icdev-student
     ↓
ICDEV Dashboard Role: developer (via role mapping in ICDEV OIDC callback)
```

### Sync Options

| Mode | Behavior |
|------|----------|
| **Read Only** | Keycloak reads AD users but does not write back. Password changes happen in AD. |
| **Read Only + Sync Registrations To LDAP** | New users created in Keycloak are also written to AD. |
| **Writable** | Keycloak can update AD attributes. |

**Recommendation:** `Read Only` for production. Your IT department manages AD; Keycloak consumes it.

### Periodic Sync

Configure `Periodic Full Sync` (e.g., every 12 hours) and `Periodic Changed Users Sync` (e.g., every 5 minutes) so new AD users appear in Keycloak quickly.

## Method 2: Kerberos/SPNEGO (Seamless Windows SSO)

If students log into a domain-joined Windows machine, Keycloak can authenticate them **without a password prompt** using the Kerberos ticket they already hold.

### Prerequisites

| Requirement | Detail |
|-------------|--------|
| Keycloak server joined to AD domain | Or a trust relationship exists |
| Service Principal Name (SPN) | `HTTP/keycloak.icdev.local@CORP.LOCAL` |
| Keytab file | Generated by `ktpass` or `setspn` on a domain admin machine |
| Browser configuration | IE/Edge/Chrome: "Automatic logon with current username and password". Firefox: `network.negotiate-auth.trusted-uris`. |

### Keytab Generation (on Windows DC)

```powershell
# Run as Domain Admin
ktpass /princ HTTP/keycloak.icdev.local@CORP.LOCAL `
       /mapuser svc_keycloak_krb `
       /crypto AES256-SHA1 `
       /ptype KRB5_NT_PRINCIPAL `
       /pass *** `
       /out keycloak.keytab
```

Upload `keycloak.keytab` to the Keycloak server and configure:
**Authentication → Kerberos → Enable**: `On`  
**Kerberos Realm**: `CORP.LOCAL`  
**KeyTab Path**: `/opt/keycloak/keycloak.keytab`  
**Server Principal**: `HTTP/keycloak.icdev.local@CORP.LOCAL`

### User Experience

1. Student logs into Windows (already authenticated to AD)
2. Opens Chrome/Edge → navigates to ICDEV dashboard
3. ICDEV redirects to Keycloak `/auth`
4. Keycloak sees `Negotiate` header with Kerberos ticket → validates against AD
5. Keycloak issues OIDC token → redirects back to ICDEV
6. Student is logged in with their AD identity — **zero password entry**

## ICDEV Integration Flow (OIDC)

Once Keycloak is federated to AD, ICDEV's existing OIDC client (`tools/saas/auth/oauth_auth.py`) connects seamlessly:

```yaml
# ICDEV .env additions
KEYCLOAK_BASE_URL=https://keycloak.icdev.local
KEYCLOAK_REALM=icdev
KEYCLOAK_CLIENT_ID=icdev-dashboard
KEYCLOAK_CLIENT_SECRET=***
KEYCLOAK_AUTH_URL=https://keycloak.icdev.local/realms/icdev/protocol/openid-connect/auth
KEYCLOAK_TOKEN_URL=https://keycloak.icdev.local/realms/icdev/protocol/openid-connect/token
KEYCLOAK_USERINFO_URL=https://keycloak.icdev.local/realms/icdev/protocol/openid-connect/userinfo
KEYCLOAK_JWKS_URL=https://keycloak.icdev.local/realms/icdev/protocol/openid-connect/certs
```

```python
# tools/dashboard/app.py — OIDC callback (simplified)
@app.route("/oidc/callback")
def oidc_callback():
    code = flask_request.args.get("code")
    
    # Exchange authorization code for token
    token = oauth_auth.exchange_code(
        code=code,
        token_url=os.environ["KEYCLOAK_TOKEN_URL"],
        client_id=os.environ["KEYCLOAK_CLIENT_ID"],
        client_secret=os.environ["KEYCLOAK_CLIENT_SECRET"],
        redirect_uri=url_for("oidc_callback", _external=True),
    )
    
    # Decode JWT (already implemented in oauth_auth.py)
    claims = oauth_auth.validate_jwt(
        token["access_token"],
        jwks_uri=os.environ["KEYCLOAK_JWKS_URL"],
    )
    
    # Extract AD-sourced identity
    email = claims.get("email")
    username = claims.get("preferred_username")
    ad_groups = claims.get("realm_access", {}).get("roles", [])
    
    # Map AD groups to ICDEV roles
    role_map = {
        "icdev-admin": "admin",
        "icdev-pm": "pm",
        "icdev-isso": "isso",
        "icdev-student": "developer",
    }
    icdev_role = next((role_map[g] for g in ad_groups if g in role_map), "developer")
    
    # Find or create user in ICDEV dashboard_users
    user = get_user_by_email(email)
    if not user:
        user = create_user(email, username, role=icdev_role)
    
    flask_session["user_id"] = user["id"]
    return redirect(url_for("index"))
```

## Security Considerations

| Concern | Mitigation |
|---------|------------|
| **LDAP traffic sniffing** | Always use `ldaps://` (port 636) with valid TLS certificate. Never `ldap://` (port 389) in production. |
| **Bind credential exposure** | Use a dedicated service account with minimal privileges (only read Users/Groups OU). Rotate password quarterly. |
| **Keytab file security** | `chmod 600 keycloak.keytab`. Store in Docker secret or K8s Secret. Never commit to Git. |
| **Certificate validation** | Ensure Keycloak trusts the AD DC's CA certificate (may need to import enterprise CA into Java truststore). |
| **Firewall rules** | Keycloak → AD DC: only TCP 636 (LDAPS) and UDP 88 (Kerberos). No direct student → AD traffic. |

---

## Comparison: LDAP vs Kerberos for ICDEV

| Factor | LDAP Only | LDAP + Kerberos (SPNEGO) |
|--------|-----------|--------------------------|
| **Setup complexity** | Low (one LDAP connection) | Medium (keytab, SPN, browser config) |
| **User experience** | Username + password prompt | Seamless (if on domain machine) |
| **Off-domain devices** | Works (prompts for AD creds) | Falls back to username/password |
| **ICDEV code changes** | Same (OIDC callback) | Same (OIDC callback) |
| **IT dependencies** | Service account + read ACLs | Service account + SPN + keytab + DNS |
| **Best for** | Mixed device environments (BYOD) | Domain-managed Windows labs |

**Recommendation:** Start with LDAP federation only. It gives you AD-backed accounts immediately with minimal IT coordination. Add Kerberos later if students are on domain-managed Windows machines and you want the seamless experience.

## Deployment in ICDEV's Docker Compose

```yaml
# docker-compose.yml addition
services:
  keycloak:
    image: quay.io/keycloak/keycloak:26.0
    command: ["start", "--optimized"]
    environment:
      KC_DB: postgres
      KC_DB_URL: jdbc:postgresql://icdev-postgres:5432/keycloak
      KC_DB_USERNAME: keycloak
      KC_DB_PASSWORD: ${KEYCLOAK_DB_PASSWORD}
      KC_HOSTNAME: keycloak.icdev.local
      KC_PROXY: edge
      KC_HEALTH_ENABLED: "true"
      KEYCLOAK_ADMIN: admin
      KEYCLOAK_ADMIN_PASSWORD: ${KEYCLOAK_ADMIN_PASSWORD}
      # LDAP federation config (can also be done via admin UI + export)
      KC_FEATURES: token-exchange
    volumes:
      - keycloak-data:/opt/keycloak/data
      - ./secrets/keycloak.keytab:/opt/keycloak/keycloak.keytab:ro
    ports:
      - "8080:8080"
    networks:
      - icdev-net
    depends_on:
      - icdev-postgres
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health/live"]
      interval: 30s
      timeout: 10s
      retries: 3
```

## Summary

| Question | Answer |
|----------|--------|
| **Can Keycloak integrate with Windows AD?** | **Yes.** Via LDAP federation (standard) and Kerberos/SPNEGO (seamless SSO). |
| **What does ICDEV need to change?** | Minimal. OIDC callback already exists in `tools/saas/auth/oauth_auth.py`. Just point it at Keycloak. |
| **Do students need new passwords?** | **No.** They use their existing Windows/AD credentials. |
| **Can AD groups map to ICDEV roles?** | Yes. Configure group-ldap-mapper in Keycloak, then map Keycloak roles → ICDEV roles in the OIDC callback. |
| **Is this required before the Anthropic proxy?** | **No.** Proxy is independent. But if you do both, you get identity-aware LLM spend attribution. |

**Bottom line:** Keycloak + AD is a mature, well-documented integration. For ICDEV, it means students log in with their Windows credentials (or seamlessly if domain-joined), and ICDEV receives OIDC tokens with AD-sourced claims. No new user database to manage.
